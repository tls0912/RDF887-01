# R007 流程規格

產出日期：2026-06-23

## 1. 目的

R007 用於將指定 `CARRIERID` 從 WIP/STK 搬送到 EQP。系統收到 ASE 的 R007 COMMAND 後，會先驗證資料與 ZIPA 產品狀態，建立 R007 任務與 inbox；之後由 `R007Walker` 分兩段處理：

1. ZIP worker：撿 R007 inbox，確認 ZIPA 可派單，決定 `STK_PORT`，送 ZIPA `DispatchOrder`。
2. AMR worker：ZIPA 接單成功後，等待 ZIPA inventory gate 成立，再轉發 R007 COMMAND 給 SEEC。

R007 最終 `END` / `FAIL` / `CANCEL` 由 `R007AckHandler` 接收 SEEC/AMR ACK 後，轉發給 ASE。

## 2. 主要元件

| 元件 | 職責 |
| --- | --- |
| `R007CommandHandler` | 接收 R007 COMMAND，驗證欄位與 ZIPA type=2 狀態，建立 `robot_in_r007`、`robot_r007_task`、`mqtt_inbox`，回覆 ACK=`OK` 或 `FAIL` |
| `R007Walker.tickZip()` | 撿 R007 inbox，檢查 ZIPA dispatch/status/inventory，決定 `STK_PORT`，送 ZIPA DispatchOrder，更新 ZIP 狀態並將 inbox DONE |
| `R007Walker.tickAmr()` | 掃描 open R007 task，確認 ZIP accepted 與 AMR gate，轉發 R007 COMMAND 給 SEEC |
| `R007AckHandler` | 接收 SEEC/AMR 的 R007 ACK，更新任務 AMR 狀態，將 final ACK 轉發 ASE |
| `RobotTaskCommandController` | UI/API 人工取消 R007，更新任務並回覆 ASE CANCEL |
| `ZipStockerEventService` | ZIPA 手動移除產品等事件會取消 R007，並送 ASE CANCEL 與 SEEC R018 |
| `RobotR007TaskRepository` | R007 任務查詢與 ZIP/AMR 狀態更新 |

## 3. COMMAND Payload

DTO：`R007CommandPayload`

### 3.1 Header

| 欄位 | 說明 | 規則 |
| --- | --- | --- |
| `CMD` | 指令類型 | 固定 `ROBOT` |
| `CMD_ID` | 指令代號 | 固定 `R007` |
| `TID` | 任務交易編號 | 必填 |
| `ID_DESC` | 指令描述 | 預期 `ROBOT_MOVE_SCH_TO_EQP` |
| `MESSAGE` | 任務內容 | 必填 |
| `RESULT` | COMMAND 來文通常不使用 | 轉發 SEEC 時設空字串 |
| `RESULT_MESSAGE` | COMMAND 來文通常不使用 | 轉發 SEEC 時設空字串 |

### 3.2 MESSAGE

| 欄位 | 型別 | 必填 | 規則 / 說明 |
| --- | --- | --- | --- |
| `LOT_ID` | String | 是 | Lot ID |
| `CARRIERID` | String | 是 | Carrier ID |
| `WIPNAME` | String | 是 | WIP/STK 名稱 |
| `DEST_LOC` | String | 是 | 目的設備/位置 |
| `EQP_PORT` | String | 是 | 目的 EQP Port |
| `DEVICE_NAME` | String | 否 | 允許空值 |
| `TRAY_HIGH` | Decimal | 是 | 必須 > 0，小數位不可超過 3 |
| `TRAY_TYPE` | String | 是 | 長度不可超過 64 |
| `TRAY_NUM` | Integer | 是 | 必須 >= 0 |
| `MOVE_PRIORITY` | Integer | 否 | 若有值，必須在 0~9 |
| `MISSION_TRIP` | String | 否 | 可由 ACK telemetry 更新 |
| `ODO` | Decimal | 否 | 可由 ACK telemetry 更新 |
| `AMR_SPEED` | Decimal | 否 | 可由 ACK telemetry 更新 |
| `AMR_ROBOT_SPEED` | Decimal | 否 | 可由 ACK telemetry 更新 |
| `PPKG_BODY_SIZE` | String | 否 | 目前驗證程式碼已註解 |
| `FLIP` | String | 是 | 只允許 `Y` 或 `N`，會轉大寫 |
| `STK_PORT` | String | 否 | ASE 來文可不帶；Walker 會決定並轉發給 SEEC |

## 4. R007CommandHandler 流程

1. normalize `MESSAGE`：
   - 字串欄位 trim。
   - 空字串轉 null。
   - `FLIP` 轉大寫。
2. 驗證必填與格式。
3. 驗證失敗時，不寫 DB，直接回覆 ACK=`FAIL`。
4. 將原始 COMMAND 記錄到 `mqtt_message_log`，取得 `logId`。
5. 查 ZIPA type=2，`name = CARRIERID`：
   - 找不到產品時，回覆 ACK=`FAIL`。
   - status 不是 `33` 時，回覆 ACK=`FAIL`。
   - status 是 `33` 才允許接單。
6. 檢查重複 open 任務：
   - 若 open 任務中已有相同 `TID`，視為重複。
   - 若 open 任務中已有相同 `CARRIERID`，也視為重複。
   - 目前 `(CARRIERID + DEST_LOC + EQP_PORT)` 的精準重複判斷已註解，實際只用 `TID` 或 `CARRIERID`。
7. 若重複，回覆 ACK=`FAIL`，不建立新任務。
8. 寫入或更新 `robot_in_r007`。
9. 寫入或更新 `robot_r007_task`。
10. 寫入 `mqtt_inbox`，priority 固定 `5`。
11. 回填 `robot_r007_task.inbox_id`。
12. 回覆 ACK=`OK`。

## 5. R007 任務資料

### 5.1 `robot_in_r007`

| 欄位 | 來源 |
| --- | --- |
| `log_id` | `mqtt_message_log.id` |
| `lot_id` | `MESSAGE.LOT_ID` |
| `carrier_id` | `MESSAGE.CARRIERID` |
| `wip_name` | `MESSAGE.WIPNAME` |
| `dest_loc` | `MESSAGE.DEST_LOC` |
| `eqp_port` | `MESSAGE.EQP_PORT` |
| `device_name` | `MESSAGE.DEVICE_NAME` |
| `stk_port` | `MESSAGE.STK_PORT`，ASE 來文通常可為 null |

### 5.2 `robot_r007_task` 建立時狀態

| 欄位 | 建立時內容 |
| --- | --- |
| `log_id` | `mqtt_message_log.id` |
| `inbox_id` | 建立 inbox 後回填 |
| `tid` | COMMAND `TID` |
| `lot_id` / `carrier_id` / `wip_name` | COMMAND MESSAGE |
| `dest_loc` / `eqp_port` / `device_name` | COMMAND MESSAGE |
| `stk_port` | 初始為 null，由 ZIP worker 決定 |
| `tray_high` / `tray_type` / `tray_num` | COMMAND MESSAGE |
| `move_priority` / `mission_trip` / `odo` | COMMAND MESSAGE |
| `amr_speed` / `amr_robot_speed` / `ppkg_body_size` / `flip` | COMMAND MESSAGE |
| `raw_message_json` | R007 MESSAGE JSON |
| `zip_required` | true |
| `zip_state` | `PENDING` |
| `zip_attempts` | 0 |
| `amr_required` | true |
| `amr_state` | `PENDING` |
| `amr_attempts` | 0 |
| `internal_state` | `QUEUED` |
| `external_last_result` | `OK` |
| `external_last_time` | 建立時間 |

`findOpen()` 判斷方式為：`external_last_result` 為 null，或不在 `END`、`FAIL`、`CANCEL`。因此 `external_last_result=OK` 仍然是 open 任務。

## 7. ZIP Worker 流程

### 7.1 基本檢查

1. 撿一筆 R007 inbox。
2. 若無 inbox，結束本輪。
3. 若 `cmd_id` 不是 R007，requeue 1 秒。
4. 依 `logId` 查 `robot_in_r007`。
5. 若找不到 `robot_in_r007`：
   - 若 task 存在，更新 task 為 `internal_state=FAILED` 並寫入 `fail_reason`。
   - inbox mark rejected。
   - 結束。
6. 依 `logId` 查 `robot_r007_task`。
7. 若找不到 task：
   - inbox mark rejected。
   - 結束。
8. 若 `carrierId` 空白：
   - inbox requeue `backoffSeconds`。
   - 結束。
9. 若 task 已是 ZIP accepted：
   - inbox mark done。
   - 結束。

### 7.2 DEST_LOC 綁定 STK_PORT

若本筆 task 尚無 `stk_port`：

1. 取 `destLoc = task.dest_loc`，若空則用 `robot_in_r007.dest_loc`。
2. 查同 `dest_loc` 且 open、已有 `stk_port` 的最新 R007 任務。
3. 若找到，沿用該 `stk_port` 並寫回本筆 task。
4. 再重新讀取本筆 task 的 `stk_port`。

此規則避免同一個 `DEST_LOC` 的多筆任務被分配到不同 STK port。

### 7.3 ZIPA 派單前檢查

1. 查 ZIPA dispatch status type=5。
2. 若任一 type=5 status 是 `62`，表示 ZIPA 有任務執行中：
   - inbox requeue `backoffSeconds`。
   - 結束。
3. 查 ZIPA type=2，`name = carrierId`。
4. 若找不到 carrier：
   - inbox requeue `backoffSeconds`。
   - 結束。
5. 若 status 不是 `33`：
   - inbox requeue `backoffSeconds`。
   - 結束。

### 7.4 決定 STK_PORT

若前面尚未取得 `stk_port`，查 ZIPA inventory type=6：

1. 讀 `STK01-OP` 的 `message[1]` 作為 carrier。
2. 讀 `STK02-OP` 的 `message[1]` 作為 carrier。
3. `message[1]` 為 null、空白或字串 `"null"` 視為空。
4. 若 `STK01-OP` 空，選 `STK01`。
5. 否則若 `STK02-OP` 空，選 `STK02`。
6. 否則視為無可用 OP 口，inbox requeue `backoffSeconds`。

### 7.5 ZIPA DispatchOrder

1. 呼叫 `taskRepo.zipMarkAttempt`：
   - `zip_attempts + 1`
   - 更新 `zip_last_attempt_time`
   - 寫入 `zip_request_json`
2. 送 ZIPA DispatchOrder：

```java
zipService.sendDispatchOrder(ZipTarget.ZIPA, List.of(carrierId), stkPort)
```

3. 若 response 第一筆 result 不是 `0`：
   - `taskRepo.zipMarkRejected`
   - inbox requeue `backoffSeconds`
   - 結束。
4. 若 result 是 `0`：
   - `taskRepo.zipMarkAccepted`
   - `upsertTaskAssignZIP` 寫入 `stk_port` 並將 `internal_state=PROCESSING`
   - inbox mark done
   - 結束。

目前 ZIP worker 成功後不在此轉發 SEEC，也不送 START ACK；AMR worker 後續掃 task 轉發。

## 8. AMR Worker 流程

AMR worker 不撿 inbox，而是掃描 `robot_r007_task.findOpenLimited(amrScanLimit)`。

### 8.1 選取候選 task

候選條件：

1. task 必須 ZIP accepted：
   - `zip_state = ACCEPTED`
   - 或 `zip_accept_time` 不為 null
2. `amr_required` 不能是 false。
3. `amr_state` 必須是 `PENDING` 或 `SENT`。
4. `stk_port` 必須有值。
5. gate cooldown 已到期：
   - wait 秒數由 task id 決定，範圍預設 5~10 秒。
   - 使用 `amr_last_attempt_time` 判斷。

### 8.2 Gate 判斷

AMR worker 查 ZIPA inventory type=6，組成位置與 carrier map。

Gate 需要同時成立：

1. `STKxx-AMR` 有產品。
   - 若 `STKxx-AMR` 空，會改看 `STKxx-OP`。
   - 若 `STKxx-OP` 也空，會改看 `STKxx-CCD`。
2. 任務 carrier 必須存在於同一個 STK group：
   - `STKxx-Buffer`
   - `STKxx-Car`
   - `STKxx-FP`
   - `STKxx-OP`
   - `STKxx-AMR`

若 gate 不成立：

1. 更新 `amr_last_attempt_time = now`。
2. 更新 `amr_result_message`：
   - `WAIT_GATE: STKxx-AMR empty`
   - 或 `WAIT_GATE: carrier not in STKxx group`
3. 不增加 `amr_attempts`。
4. 不改 `amr_state` 為 `SENT`。
5. 結束本輪。

### 8.3 轉發 SEEC

若 gate 成立：

1. 讀取 `amr_attempts`。
2. 判斷是否已送過：
   - `amr_state = SENT` 表示已送過。
3. 判斷 timeout：
   - `amr_last_attempt_time + amrTimeoutSeconds < now`
4. 若尚未送過，或已送過且 timeout 且 attempts 未達上限，則轉發 SEEC。
5. 第一次轉發使用原始 R007 `tid`。
6. 重送時產生新的 TID。
7. 從 task 與 `robot_in_r007` 組成 R007 COMMAND：
   - Header 固定 `CMD=ROBOT`、`CMD_ID=R007`、`ID_DESC=ROBOT_MOVE_SCH_TO_EQP`
   - `RESULT` / `RESULT_MESSAGE` 設空字串
   - MESSAGE 以 task 為主，不足則用 `robot_in_r007`
   - `STK_PORT` 使用 ZIP worker 決定的 `stk_port`
8. 記錄 `mqtt_message_log`，topic/source 為 `cmd/r007/forward`。
9. publish 到 `seec`。
10. 呼叫 `taskRepo.amrMarkSent`：
    - `amr_state = SENT`
    - `amr_attempts + 1`
    - `amr_last_attempt_time = now`
    - `amr_tid = forward.tid`
    - `amr_forward_log_id`
    - `amr_request_json`

若已送過但未 timeout，直接等待 ACK。

若 timeout 且已達最大次數：

1. 更新 `internal_state=FAILED`。
2. 寫入 `fail_reason = AMR timeout and max attempts reached`。

## 9. ACK 流程

### 9.1 CommandHandler 回 ASE

`R007CommandHandler` 回覆：

| RESULT | 說明 |
| --- | --- |
| `OK` | R007 驗證成功，已建立 task 與 inbox |
| `FAIL` | 欄位錯誤、ZIPA 狀態不允許、重複任務、DB 錯誤或例外 |

Handler 回覆 ACK 時，不帶 `STK_PORT`。

### 9.2 R007AckHandler 接收 SEEC/AMR ACK

R007AckHandler 流程：

1. 記錄收到的 ACK 到 `mqtt_message_log`。
2. 用 ACK 的 `TID` 查 `robot_r007_task.amr_tid`。
3. 找不到 task 時只記 log 並結束。
4. 若 ACK MESSAGE 有 telemetry，更新 task：
   - `MISSION_TRIP`
   - `ODO`
   - `AMR_SPEED`
   - `AMR_ROBOT_SPEED`
5. 依 RESULT 更新 AMR 狀態：

| RESULT | task 更新 | 是否轉發 ASE |
| --- | --- | --- |
| `OK` | `amr_state=OK`，記錄 ACK log/json/time | 否 |
| `START` | `amr_state=START`，記錄 ACK log/json/time | 否 |
| `END` | `amr_state=END`，`external_last_result=END`，`internal_state=COMPLETED` | 是 |
| `FAIL` | `amr_state=FAIL`，`external_last_result=FAIL`，`internal_state=FAILED` | 是 |
| `CANCEL` | `amr_state=CANCEL`，`external_last_result=CANCEL`，`internal_state=CANCELLED` | 是 |

`CANCLE` 會被 normalize 成 `CANCEL`。

轉發 ASE 時使用原始 R007 task 的 `tid`，不是 AMR 轉發時的 `amr_tid`。

## 10. 取消流程

### 10.1 UI/API 取消

`RobotTaskCommandController.cancelR007`：

1. 依 task id 查 `robot_r007_task`。
2. 更新：
   - `external_last_result = CANCEL`
   - `external_last_time = now`
   - `cancel_reason = reason`
   - `internal_state = CANCELLED`
3. 發 R007 ACK=`CANCEL` 給 ASE。

目前 controller 中「已終態略過」判斷是註解狀態，因此即使任務已終態也會更新取消。

`sendR007CancelToSEEC` 方法存在，但 UI/API 取消流程目前沒有呼叫它。

### 10.2 ZIPA 事件取消

`ZipStockerEventService.cancelR007`：

1. 更新 task 為 CANCELLED。
2. 發 R007 ACK=`CANCEL` 給 ASE。
3. 發 R018 給 SEEC，`CMD_TID = R007_<原始 tid>`。

## 11. 等待、重試或終止條件

| 條件 | 處理 |
| --- | --- |
| Command 欄位驗證失敗 | ACK=`FAIL`，不入隊 |
| ZIPA type=2 找不到 carrier | ACK=`FAIL`，不入隊 |
| ZIPA type=2 status 不是 33 | ACK=`FAIL`，不入隊 |
| open 任務已有相同 TID | ACK=`FAIL`，不入隊 |
| open 任務已有相同 CARRIERID | ACK=`FAIL`，不入隊 |
| ZIP worker 找不到 `robot_in_r007` | inbox rejected，task 若存在則 FAILED |
| ZIP worker 找不到 `robot_r007_task` | inbox rejected |
| ZIP worker carrierId 空白 | inbox requeue `backoffSeconds` |
| task 已 ZIP accepted | inbox mark done |
| ZIPA type=5 status=62 | inbox requeue `backoffSeconds` |
| ZIPA type=2 查不到 carrier | inbox requeue `backoffSeconds` |
| ZIPA type=2 status 不是 33 | inbox requeue `backoffSeconds` |
| 無可用 OP 口 | inbox requeue `backoffSeconds` |
| ZIPA DispatchOrder result 不是 0 | zip_state=REJECTED，inbox requeue |
| ZIPA DispatchOrder 成功 | zip_state=ACCEPTED，task PROCESSING，inbox DONE |
| AMR gate 不成立 | touch `amr_last_attempt_time`，等待下次掃描 |
| AMR 已 SENT 但未 timeout | 等待 ACK |
| AMR timeout 且 attempts 未達上限 | 重新轉發 SEEC |
| AMR timeout 且 attempts 達上限 | task `internal_state=FAILED` |
| SEEC 回 END | task COMPLETED，轉發 ASE END |
| SEEC 回 FAIL | task FAILED，轉發 ASE FAIL |
| SEEC 回 CANCEL/CANCLE | task CANCELLED，轉發 ASE CANCEL |

## 12. 目前程式碼注意事項

1. R007 ZIP worker 使用 `pickOneForProcessingByCmdNoNextAttemptTime`，會忽略 `next_attempt_time`。
2. `R007Walker` 內有 `sendAckStart` 方法，但目前 ZIP accepted 後沒有送 START ACK；AMR 轉發 SEEC 後也因沒有 inbox sender，註解明確說目前不回 START ACK 給原來源。
3. STK_PORT 決策目前只會從 `STK01-OP`、`STK02-OP` 找空位，選 `STK01` 優先，再選 `STK02`；不會選 STK03~STK05。
4. 同 `DEST_LOC` 會沿用 open 任務已有的 `stk_port`，可能讓後續任務跳過 OP 空位選擇。
5. AMR gate 的 `isStkAmrHasProduct` 會 fallback 看 `STKxx-CCD`，但 `isCarrierInStkGroup` 的群組不包含 `CCD`。
6. `processAmrOnce` 掃描候選時，多個不符合條件的分支使用 `return` 而不是 `continue`，可能因第一筆 open task 不符合條件而不掃後續 task。
7. `processAmrOnce` 中 `if (task == null) return;` 被註解；若候選清單都被 `continue` 跳過，後續取 `task.getLogId()` 可能丟 NPE，雖然外層會 catch。
8. `RobotTaskCommandController.cancelR007` 目前沒有檢查終態，也沒有呼叫 `sendR007CancelToSEEC`。
9. `zipMarkRejected` 只更新 ZIP 狀態，不會把 `external_last_result` 設成 `FAIL`；因此任務仍可能被 `findOpen()` 視為 open。
